# 정책정의서

- 서비스가 판단·제한·표시할 때 따르는 기준과 그 이유
- 값의 기준은 코드: 판단 `src/core/triage.ts`, 제한값 `src/config.ts`. 문서와 코드가 다르면 코드가 기준

## 1. 자동 발송 기준

- 아래를 **모두** 만족할 때만 고객에게 자동 발송. 하나라도 걸리면 상담원에게 넘기고 사유를 남김
- 기준은 코드 한 곳에서 판단. 프롬프트에 맡기지 않음

| 순서 | 조건 | 걸리면 | 이유 |
|:---:|---|---|---|
| 1 | 정책을 묻는 질문 (조치 요청이 아님) | 개인 처리 요청 | "환불해 주세요"는 답이 맞아도 실제 처리는 사람이 해야 함 |
| 2 | 답변 상태가 확정 | 근거 없음 · 준비 중 정책 | 준비 중 정책은 가격·출시일처럼 불만이 큰 주제 → 1차는 전부 넘기고 운영 데이터를 본 뒤 결정 |
| 3 | 확신도 높음 | 저확신 | 사람 확인 없이 나가는 답은 코파일럿보다 한 단계 보수적으로 |
| 4 | 답장에 근거 밖 숫자 없음 | 근거 밖 숫자 | 금액·기간 같은 숫자 오류가 가장 비싼 사고 |
| - | 모델 호출 성공 | 처리 실패 | 실패해도 문의 접수는 유지 |

- 운영 원칙: 잘못된 자동 발송 0건이 자동 처리율보다 우선
  - 1차 평가에서 자동 발송하지 못한 3문항은 모두 저확신(고객 말투라 검색 유사도 0.39~0.48) → 기준을 낮추지 않고 유지, 조정은 평가셋으로 검증할 실험으로 분리

## 2. 넘김 사유

| 코드 | 화면 라벨 | 발생 조건 | 상담원이 할 일 |
|---|---|---|---|
| `action_request` | 개인 처리 요청 | 고객이 조치를 요청 | 실제 처리(환불·해지·도용 조치) 후 결과 안내 |
| `unanswerable` | 근거 없음 | 정책 문서에 근거가 없음 | 담당 부서 확인 후 답변, 문서 보강 요청 |
| `pending_policy` | 준비 중 정책 | 준비 중 문서가 근거 | 요금·일정 약속 없이 안내 |
| `low_confidence` | 저확신 | 확정 답변이지만 확신도 보통·낮음 | 인용 원문 확인 후 초안 수정 |
| `unsupported_numbers` | 근거 밖 숫자 | 답장에 근거에 없는 숫자 | 숫자 확인·수정 |
| `error` | 처리 실패 | 모델 호출 실패 | 직접 답변 |

## 3. 답변 상태와 확신도

### 답변 상태

| 상태 | 코드 | 조건 | 표시 |
|---|---|---|---|
| 확정 답변 | `answered` | 확정 문서에 근거가 있고 인용이 있음 | 초록, "근거 문서를 확인한 뒤 안내" |
| 준비 중 정책 | `pending_policy` | 근거가 준비 중 문서 | 주황, "요금·일정을 약속하지 말 것" |
| 근거 없음 | `unanswerable` | 검색 결과 없음, 모델이 근거 부족 판단, 또는 인용 없음 | 빨강, "추측하지 말고 담당자 확인" |

- 코드가 교정하는 경우
  - 검색 결과가 없으면 모델을 부르지 않고 근거 없음
  - 모델이 답했다고 해도 인용이 없으면 근거 없음
  - 준비 중 문서를 인용해 확정 답을 내면 준비 중 정책

### 확신도

- 검색 신호(최고 유사도)와 모델 신호(근거 충분 여부) 중 **약한 쪽**
- 검색 신호 기준: 최고 유사도 0.5 이상 높음 · 0.35 이상 보통 · 그 아래 낮음
- 확정 답변에만 표시. 낮음이면 "인용 원문을 직접 확인" 경고
- 거절(근거 없음) 판단은 유사도가 아니라 모델의 근거 판단이 담당
  - 이유: 답해야 하는 구어체 질문과 거절해야 하는 질문의 유사도 구간이 겹침 → 유사도 하한(0.15)은 명백히 무관한 조각만 거름

## 4. 고객 답장 작성 규칙

| 규칙 | 내용 | 보장 방식 |
|---|---|---|
| 입력 제한 | 확인된 답변과 인용 근거만. 원 문서 전체나 검색 결과는 넣지 않음 | 서버 저장 답변(`answerId`)으로만 요청 |
| 사실 추가 금지 | 수치·일정·절차 추가 금지, 근거 없는 시점 약속 금지 | 프롬프트 + 근거 밖 숫자 코드 검사 |
| 상태별 작성 | 확정은 결론 먼저, 준비 중은 "확정되면 공지로 안내"만, 근거 없음은 보류 답장 | 프롬프트 |
| 조치 요청 | 확인 전에 결과를 약속하지 않음 ("환불해 드리겠습니다" 금지) | 요청 유형 전달 + 프롬프트 + 코드 검사 |
| 내부 표현 제거 | 문서 이름·조각 번호·"상담원" 같은 내부 표현을 고객 관점 문장으로 | 프롬프트 |
| 인사말 | 첫 줄 "안녕하세요. 시네웨이브입니다." | 코드가 교체 |
| 형식 | 마크다운 금지, 5문장 안팎 | 프롬프트 |

## 5. 호출 제한과 비용

| 항목 | 값 | 이유 |
|---|---|---|
| 질문 길이 | 300자 | 긴 입력으로 비용을 키우는 것 방지 |
| IP별 분당 요청 | 20회 | 연타 방지. 처음 6회 → 질문 하나에 답변·답장 2번이라 예시 몇 개만 눌러도 걸려서 조정 |
| IP별 하루 모델 호출 | 30회 | 한 방문자가 전체 한도를 다 쓰지 못하게 먼저 확인 |
| 전체 하루 모델 호출 | 300회 | 넘으면 목업 모드로 전환 |
| 같은 질문 캐시 | 24시간 | 캐시 적중은 모델을 부르지 않아 상한에 포함하지 않음 |
| 하루 모델 비용 예산 | 1달러, 80%에서 알림 | 차단은 호출 상한이 맡고 예산은 경보용 |
| 답장 초안 | 버튼을 누를 때만, 만든 초안은 재사용 | 모든 질문에 호출이 두 배가 되는 것 방지 |

## 6. 개인정보

- 고객 문의는 **저장·모델 호출 전에** 가림 (공개 데모라 다른 방문자에게 보이고 모델에도 들어감)

| 대상 | 표시 |
|---|---|
| 이메일 | `[이메일]` |
| 주민등록번호 (13자리) | `[주민등록번호]` — 카드 번호 규칙에도 걸리므로 먼저 처리 |
| 카드 번호 (13~16자리) | `[카드번호]` |
| 휴대전화 번호 | `[전화번호]` |

- 문의 창에 "개인정보 입력 금지" 안내 상시 표시
- DB는 모든 테이블 RLS를 켜고 정책을 두지 않음, 서버 역할만 접근

## 7. SLA와 알림

| 항목 | 기준 |
|---|---|
| SLA | 상담원 대기 30분 |
| SLA 확인 주기 | n8n이 10분마다 대기 초과 티켓 조회 |
| 재알림 | 같은 티켓은 60분마다 |
| 넘김 알림 | 넘김 즉시 Slack (티켓 링크·사유·대기). n8n 실패 시 API가 직접 전송하고 '알림 실패' 기록 |
| 운영 알림 | 대체 모델 전환, 서버 오류(500), 하루 예산 80%, 헬스체크 실패. 같은 알림은 30분에 한 번 |

## 8. 모델

| 항목 | 기준 | 이유 |
|---|---|---|
| 기본 생성 모델 | `gemini-3.8-flash` | 모델 10개를 같은 평가셋으로 비교해 선택 ([model-selection.md](../model-selection.md)) |
| 대체 모델 | `gpt-5.4-mini` | 기본 모델과 **다른 제공사** — 한 제공사 장애에 같이 멈추지 않게 |
| 전환 조건 | 일시 오류(시간 초과·5xx·429), 제공사 문제(401·403·404) | 요청 자체 오류(400·422)는 코드·스키마 버그라 전환하면 원인을 가림 |
| 임베딩 | `text-embedding-3-small`, 대체 없음 | 문서 수십 개 규모에서 비용 대비 충분. 4초 제한·1회 재시도 |

## 9. 공개 데모 운영

| 항목 | 기준 |
|---|---|
| 권한 | 로그인 없음. 방문자 누구나 상담원·고객 역할 체험 |
| 목업 모드 | 호출 상한 초과·서버 연결 실패 시 평가 때 저장한 실제 응답으로 동작, 화면에 이유 표시 |

| 데이터 | 회사·요금·정책·문의 모두 가상. 실존 서비스와 무관 |
