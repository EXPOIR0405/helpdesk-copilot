# 배운 것

- 상담원용 정책 답변 코파일럿을 설계·평가·배포·운영하며 배운 것
- 항목마다 상황 → 배운 것 → 이후 적용 순서
- 수치와 근거는 [`architecture.md`](../architecture.md)의 평가 기록 참고

## 1. 모르는 것을 모른다고 하는 게 기능이다

- 상황
  - 상담원이 코파일럿 답을 그대로 고객에게 전하면, 틀린 답 하나가 재문의·불만으로 돌아옴
  - 반대로 너무 자주 거절하면 상담원이 도구를 안 씀
- 배운 것
  - 지표 우선순위를 먼저 정해야 설계가 정해짐: 잘못된 답변률 0%를 첫째, 과잉 거절률을 둘째로
  - "정답률" 하나로 보면 두 실패가 섞여서 무엇을 고칠지 안 보임
- 적용
  - 평가 지표를 잘못된 답변률 · 과잉 거절률 · 상태 정확도 · 검색 적중률로 나눠 기록
  - 답변 상태를 세 가지로 나눔: 확정 답변 · 준비 중 정책 · 근거 없음

## 2. 검색 점수로는 거절을 못 한다

- 상황
  - 처음엔 유사도 하한(0.3)으로 "근거 없음"을 거르려 함
  - 1차 평가 과잉 거절률 18.8%, 틀린 6문항 중 5개가 구어체 질문
- 배운 것
  - 답해야 하는 질문과 거절해야 하는 질문의 유사도 분포가 겹침 (0.3 미만 ~ 0.69 vs 최대 0.48)
  - 분포가 겹치면 임계값을 아무리 조정해도 한쪽 실패를 다른 쪽으로 옮길 뿐
- 적용
  - 하한은 명백히 무관한 조각만 거르게 낮추고(0.15), 거절은 모델이 조각 안에서 근거를 찾았는지로 판단
  - 과잉 거절률 18.8% → 6.3%, 잘못된 답변률 0% 유지
  - 임계값을 정하기 전에 두 분포부터 그려 볼 것

## 3. 모델 판단은 믿되, 검증할 수 있는 규칙은 코드로

- 상황: 프롬프트로 "근거 없으면 거절", "준비 중이면 확정처럼 말하지 말 것"을 지시해도 100%라는 보장은 없음
- 배운 것: 규칙으로 확인할 수 있는 불변식은 프롬프트와 코드 양쪽에 둠
- 적용
  - 검색 결과가 없으면 모델을 아예 부르지 않음
  - answered인데 인용 조각이 없으면 근거 없음으로
  - 준비 중 문서를 인용한 확정 답은 준비 중 정책으로
  - 고객 답장의 숫자가 답변·근거에 없으면 경고, 첫 줄 인사말도 코드가 맞춤
  - 가드마다 단위 테스트

## 4. 한 번의 호출에 두 가지 일을 시키지 않는다

- 상황: 상담원용 답변과 고객에게 보낼 문장은 목적이 다름 (정확성·근거 vs 말투·고객 관점)
- 배운 것
  - 한 번에 시키면 둘 다 흐려짐. 단계를 나누면 각 단계의 입력을 좁힐 수 있음
  - 두 번째 단계 입력을 "확인된 답변 + 인용 근거"로 좁히자 새 사실이 끼어들 여지가 줄어듦 (초안 42건 중 근거 밖 숫자 0건)
- 적용
  - 고객 답장은 상담원이 근거를 본 뒤 버튼을 눌러야 생성 → 사람 확인 단계를 흐름에 넣음
  - 실제 출력을 읽고 프롬프트를 고침: 상담원 말투 메모("고객한테 설명해야 해요")에 초안이 상담원에게 말하듯 써져서 "고객에게 직접 말하듯" 규칙 추가

## 5. 그럴듯한 개선도 평가셋 앞에서는 손해일 수 있다

- 상황: 구어체 질문의 어휘 차이를 줄이려고 질문 재작성(소형 모델로 정책 용어로 바꿔 검색)을 시도
- 배운 것
  - 한 문항은 고쳤지만 다른 문항이 새로 실패, 검색 적중률 34 → 33
  - 재작성 프롬프트 문구 하나에 결과가 흔들림. 호출 1회와 새 실패 지점이 늘어나는 비용
  - 평가셋이 없었다면 "고쳐졌다"는 한 사례만 보고 채택했을 것
- 적용
  - 개선안은 전체 평가셋으로 전후 비교한 뒤 결정, 채택하지 않은 실험도 기록
  - 어휘 차이는 운영 루프(미답변 리포트 → 문서 보강)로 줄이는 쪽을 택함

## 6. 평가셋에는 함정 문항을 넣는다

- 상황: 쉬운 질문만 있으면 수치는 높게 나오지만 실제 위험을 못 봄
- 배운 것: 실패하기 쉬운 유형을 일부러 넣어야 설계 결정의 근거가 생김
- 적용
  - 유형을 나눔: 직접 질문 · 구어체 · 여러 문서 조합 · 준비 중 정책 · 문서에 없는 질문
  - 함정 예: 문서에 "해외 시청"이 없는데 그럴듯하게 답하고 싶어지는 질문, 표 한 줄에만 있는 "연간 결제 상품 없음"
  - 남은 실패 2건(q13, q42)도 원인과 함께 기록 → 다음 개선 대상이 명확

## 7. 임베딩은 결정적이지 않다

- 상황: 로컬에서 Supabase(pgvector)로 옮긴 뒤 42문항 중 1문항의 검색 순서가 달라짐
- 배운 것
  - 원인을 좁혀 보니 pgvector 계산은 로컬과 같음 (같은 벡터로 42/42 동일)
  - 차이는 같은 텍스트를 다시 임베딩한 데서 생김 (코사인 평균 0.99998, 최소 0.99913)
  - "저장소를 바꿨더니 결과가 다르다"에서 멈추지 않고 변수를 하나씩 고정해 보는 게 중요
- 적용
  - 해시 기반 증분 동기화를 비용 절감만이 아니라 결과 안정성 장치로도 봄
  - 평가 수치는 소수점보다 실패 문항과 잘못된 답변률 추세로 판단

## 8. 제한값은 배포해서 직접 써 보고 정한다

- 상황: IP당 분당 6회로 시작 → 배포 직후 예시 질문 몇 개와 답장을 눌렀더니 제한에 걸림
- 배운 것
  - 질문 하나에 답변·답장 2번이라 실제 사용 패턴에 비해 너무 빡빡했음
  - 제한 하나에 연타 방지와 비용 방어를 같이 맡기면 둘 다 어정쩡해짐
- 적용
  - 역할을 나눔: 분당 20회(연타 방지) + IP별 하루 모델 호출 30회 + 전체 하루 300회(비용 상한)
  - 캐시 적중은 하루 상한에 세지 않고, 한도에 걸리면 오류 대신 목업 모드로 데모를 계속 보여줌

## 9. 서버리스에서는 동시에 들어오는 첫 요청을 가정한다

- 상황: 배포 테스트에서 답장 요청이 방금 만든 답변을 찾지 못함
- 배운 것
  - 화면이 두 API를 동시에 호출하고, 초기화를 `await` 뒤에 값으로 저장해서 런타임이 두 개 생김
  - 로컬에서 한 번에 하나씩 호출할 때는 안 보이던 문제. 실제 화면 흐름으로 테스트해야 드러남
- 적용
  - 초기화는 값이 아니라 Promise를 저장, 실패하면 다음 요청에서 다시 시도
  - 인스턴스 메모리에 기대는 상태(답변 보관, 호출 제한)는 DB로

## 10. 데모 링크는 깨지지 않아야 한다

- 상황: 포트폴리오 데모는 언제 열릴지 모름. 무료 DB는 일주일 무요청이면 일시정지, API 한도도 있음
- 배운 것: "지금 안 됨"을 보여주는 것보다 "제한된 상태로라도 동작"이 낫다
- 적용
  - 평가 때의 실제 모델 응답으로 목업 데이터를 만들고, API를 쓸 수 없으면 화면이 자동 전환하며 이유 표시
  - 하루 한 번 Cron으로 DB를 깨움 (비밀값 확인, 지난 제한 기록 정리)

## 11. 사람이 근거를 바로 확인할 수 있어야 쓴다

- 상황: 답만 보여주면 상담원이 맞는지 판단할 방법이 없음
- 배운 것: 신뢰는 답의 품질만이 아니라 "확인하기 쉬운가"에서 나옴
- 적용
  - 근거 문서는 기본으로 펼침, 근거 카드에서 원문 섹션으로 바로 이동
  - 정책 문서 탭의 원문 = 코파일럿이 검색하는 원문 (같은 동기화로 저장)
  - 확신도가 낮으면 "인용 원문을 직접 확인" 경고, 검색 추적 패널에서 어떤 조각을 근거로 썼는지 표시

## 12. 개발 환경이 바뀌면 안전장치가 조용히 꺼질 수 있다

- 상황
  - Windows에서 저장소를 새로 받아 테스트를 돌렸더니 47개 중 1개 실패: 문서 제목이 파일명으로 나옴
  - Windows git은 체크아웃할 때 줄바꿈을 CRLF로 바꾸는데(`core.autocrlf=true`), frontmatter 파서는 `\n`만 인식
- 배운 것
  - 제목만 틀린 게 아니라 frontmatter 전체를 못 읽음 → `status: pending`이 사라져 **준비 중인 광고형 요금제가 확정 정책으로** 바뀜
  - "준비 중 문서를 확정처럼 답하지 않는다" 가드가 오류 없이 꺼짐. 이 상태로 `npm run sync`하면 그대로 DB에 올라감
  - 해시도 원문 기준이라 모든 문서가 바뀐 것으로 보여 전부 다시 임베딩 → 7번의 검색 순위 흔들림이 다시 생김
  - 문서 개수를 세는 테스트가 있어서 잡혔음. 테스트가 없었다면 운영에서 확인했을 문제
- 적용
  - 파서가 줄바꿈부터 정규화 (코드 쪽 방어) + CRLF 입력 테스트
  - `.gitattributes`로 저장소 전체 LF 고정 (원인 쪽 차단)

## 13. 한 번 돌린 평가는 믿을 수 없다

- 상황
  - 모델 비교 전에 기준점으로 기존 운영 모델(`gpt-5.4-mini`)을 다시 평가
  - README의 40/42·잘못된 답변 0이 38/42·잘못된 답변 1로 나옴. 설정은 그대로
- 배운 것
  - 같은 모델·같은 프롬프트도 실행마다 판단이 달라짐. 다시 돌리면 40/42·0으로 돌아옴
  - 한 번 실행한 결과로 모델을 비교하면 모델 차이인지 우연인지 구분이 안 됨
- 적용
  - `--runs 3`: 합산 비율 + 최악 회차 + 회차마다 판단이 바뀐 문항을 함께 기록
  - 모델 선택은 1~2건 차이가 아니라 "여러 조건에서 반복되는 패턴"으로 판단 ([model-selection.md](model-selection.md))

## 14. 실패를 안전한 쪽으로 채점하면 장애가 성과로 보인다

- 상황
  - `gemini-2.5-flash-lite` 평가에서 126건이 전부 404 (`no longer available to new users`)
  - 결과표는 잘못된 답변률 0%. 실패한 호출을 "답하지 않음"으로 채점했기 때문
  - 비교표가 잘못된 답변률로 정렬하니 아무것도 못 한 모델이 1위에 오를 뻔함
- 배운 것
  - "틀린 답을 하지 않는다"를 최우선 지표로 두면, 아무 답도 못 하는 상태가 가장 좋아 보임
  - 지표가 좋아 보이면 먼저 측정이 제대로 됐는지 확인
- 적용
  - 호출 실패율 20% 초과 시 평가 무효: 남은 회차 중단, 결과 저장 안 함
  - 비교표에서 호출 실패가 있는 모델은 맨 뒤, ⚠ 표시
  - 평가 결과에 프롬프트 버전을 저장해 조건이 다른 결과끼리 섞이지 않게

## 15. 프롬프트 규칙은 좁게, 멈출 지점은 먼저

- 상황
  - q41 "TV 앱 다운로드 언제 생기나요?"를 10개 중 8개 모델이 "TV 앱은 불가"라고만 답하고 answered로 판단
  - 여러 모델이 같은 방식으로 틀림 → 모델이 아니라 프롬프트 규칙의 빈틈
- 배운 것
  - 1차 "시점이 없으면 거절": q41은 고쳤지만 응대 기준이 있는 "다음 시즌 언제?"까지 거절 → 과잉 거절 증가
  - 2차 "응대 기준이 있으면 예외": `gpt-5-mini`가 다른 주제의 기준을 끌어다 "스포츠 생중계 해요?"에 답함
  - 규칙 하나가 모델마다 다르게 읽힘. 한 모델로만 확인했다면 2차의 부작용을 못 봤음
  - 42문항에 맞춰 계속 고치면 평가셋에만 맞는 프롬프트가 됨
- 적용
  - 규칙을 바꿀 때마다 대표 모델 6개 × 3회로 전후 비교, 시작 전에 "3차까지"로 멈출 지점을 정함
  - 3차 채택: 6개 모델 잘못된 답변 합계 9 → 3, 과잉 거절 변화 없음. `gpt-5-mini`의 q40은 미해결로 기록
  - 평가셋 밖 질문(홀드아웃)으로 다시 확인하는 일을 백로그에

## 16. 대체 모델은 시간 예산과 실패 분류로 설계한다

- 상황
  - 대체 모델 전환을 붙이려고 보니 모델 호출 하나가 최대 90초 (OpenAI SDK 기본 타임아웃에 재시도 2번, Gemini 재시도 대기 28초)
  - Vercel 함수 제한은 30초 → 대체 모델로 넘어가기 전에 함수가 끝남
  - 처음엔 "4xx는 코드 버그라 넘기지 않음"으로 설계. 그런데 실제로 본 `gemini-2.5-flash-lite` 404는 코드 버그가 아니라 모델 종료
- 배운 것
  - 재시도·타임아웃 기본값은 "한 번의 호출"만 보고 정해짐. 요청 전체의 시간 예산에서 거꾸로 나눠야 함
  - 제공사 장애 중에는 같은 곳에 다시 보내도 대부분 실패 → 다른 제공사로 넘기는 것이 더 나은 재시도
  - 넘기지 말아야 할 실패는 "요청이 잘못된 것"(400·422)뿐. 키 폐기·권한·모델 종료(401·403·404)는 오히려 넘겨야 하고, 사람이 조치해야 하므로 더 강하게 알려야 함
- 적용
  - 서비스 호출 프로필: 10초·재시도 없음 → 기본 + 대체 + 임베딩·DB가 30초 안에. 평가는 30초·4회로 따로
  - 실패 분류: 일시(429·5xx·타임아웃) → 대체 + warn 알림, 제공사(401·403·404) → 대체 + error 알림, 요청 오류(400·422) → 그대로 실패
  - 404 모델을 기본으로 두고 실제 호출해 대체 모델이 2.2초 만에 응답하는 것 확인

## 17. 사람 확인이 빠지면 기준을 코드로, 평가셋을 새로

- 상황
  - 코파일럿(상담원이 확인 후 전달)을 자동 응대(바로 고객에게)로 바꾸면서 틀린 답 하나의 비용이 커짐
  - "환불은 어디서 해요?"와 "환불해 주세요"는 같은 정책 문서로 답할 수 있지만, 뒤의 것은 사람이 실제로 처리해야 하는 요청
- 배운 것
  - 기존 평가셋(상담원 말투 42문항)으로는 자동 발송이 안전한지 알 수 없음 → 고객 말투 · 조치 요청 · 비슷한 말 다른 의도 쌍이 들어간 평가셋이 따로 필요
  - 지표도 바뀜: "잘못된 답변"보다 **"넘겨야 하는데 자동으로 보낸 건"**이 최우선
- 적용
  - 판단 출력에 requestType(question·action) 추가, 자동 발송 기준은 `src/core/triage.ts` 한 곳 (조치 요청 → 근거 없음 → 준비 중 → 저확신 → 근거 밖 숫자 순)
  - 자동 응대 평가 22문항: 잘못된 자동 발송 0/33, 조치 요청 분류 18/18 (기본·대체 모델 모두)
  - 프롬프트 예시는 평가셋에 없는 주제(이용권 등록)로 → 평가셋 답을 프롬프트에 미리 알려 주지 않게
  - 판단 프롬프트가 바뀌었으니 기존 42문항도 다시 돌려 회귀 없음 확인

## 18. 로컬에서 끝까지 돌려 봐야 보이는 것

- 상황: 단위 테스트 99개가 통과한 뒤, 로컬 API + n8n + 실제 모델로 문의 → 넘김 → 알림 → 상담원 답장 → SLA 알림을 끝까지 돌림
- 배운 것 (테스트로는 안 보였던 것 세 가지)
  - **임베딩은 대체 경로가 없는 단일 장애점**: OpenAI 임베딩이 몇 분간 멈추자 문의가 "처리 실패"로 넘어감. 생성 모델용 설정(10초·재시도 없음)을 임베딩에도 쓰고 있었고, 실패 기록엔 모델 이름만 있어 어느 단계인지 추리해야 했음
  - **설계 단계의 휴리스틱이 가장 필요한 곳에서 실패**: 비슷한 과거 티켓을 "가장 가까운 문서가 같은 티켓"으로 찾았는데, 근거 없는 문의는 가까운 문서부터 엉뚱함 (해외 시청 → 쿠폰 0.27)
  - **"떠 있음"과 "준비됨"은 다름**: n8n `/healthz`가 OK를 준 뒤에도 webhook 등록은 몇 초 뒤라 그 사이 알림이 404
- 적용
  - 임베딩 전용 시간 예산(4초·1회 재시도), 실패 메시지에 "임베딩 실패:" 단계 표시
  - 비슷한 과거 티켓은 질문 벡터 유사도로. 기준 0.5는 실측(같은 뜻 0.56~0.80, 다른 주제 0.10~0.44)으로
  - n8n 알림이 실패하면 API가 Slack으로 직접 보내고 notify_failed로 기록 → 재시작 중에도 알림이 사라지지 않음을 실제로 확인
