# helpdesk-copilot 설계 문서

- 작성일: 2026-09-26
- 상태: 1단계 설계 확정 전 초안

## 1. 한 줄 요약

- 가상 OTT 회사 시네웨이브(CineWave) 고객센터 상담원용 답변 코파일럿
- 사내 정책 문서를 근거로 답변하고, 확신이 없으면 모른다고 답하는 것이 핵심
- 답하지 못한 질문을 모아 "어떤 문서가 비어 있는지" 운영자에게 알려줌

## 2. 목표와 비목표

### 목표

- 채용 담당자가 링크 하나로 바로 써볼 수 있는 웹 데모
- AI 설계 판단(검색, 확신도, 거절, 평가, 비용 방어)이 코드와 문서에서 읽히는 구조
- 핵심 엔진과 채널(웹, Slack)의 분리

### 비목표 (1단계)

- 고객 직접 응대 챗봇 — 상담원 보조 도구로 한정
- 벡터 DB, 외부 검색 인프라 도입 — 문서 규모상 불필요
- 로그인, 권한 관리
- 다국어

## 3. 가상 회사: 시네웨이브(CineWave)

### 회사 설정

- 국내 OTT 스트리밍 서비스. 드라마·영화·예능·오리지널 콘텐츠 제공
- 고객센터 상담원이 채팅·전화 문의를 받으며 정책 문서를 수시로 확인
- 가상 회사·요금·정책·오류 코드는 전부 데모용으로 지어낸 내용. 실존 서비스와 무관

### 문제 상황

- 상담 인력이 회전문처럼 드나듦 → 숙련자가 쌓은 지식이 사람과 함께 빠져나감
- 정책 문서는 많고 자주 바뀌지만, 어느 문서가 최신인지는 오래 일한 사람의 기억에만 있음
- 신입은 선배에게 같은 질문을 반복하고, 선배는 응대와 질문 답변을 동시에 떠안음
- 상담원마다 같은 문의에 다른 답을 하게 됨 → 재문의·불만 증가 → 고객 만족도 하락
- 정작 어떤 문서가 비어 있거나 낡았는지는 아무도 모름

## 4. 1단계 범위

1. **문서 동기화**: 문서 폴더 → 조각 분할 → 임베딩 → 인덱스 파일 저장. 변경된 문서만 다시 처리
2. **근접 조각 선별**: 질문 임베딩과 유사도 상위 조각 선택
3. **확신도 답변**: 근거 조각만으로 답변 생성, 확신도(높음/보통/낮음)와 인용 조각 함께 반환
4. **미답변 리포트**: 확신도 낮음·거절 질문 기록, 비슷한 질문끼리 묶어 운영 화면에 표시

## 5. 아키텍처

```
            ┌───────────── adapters ─────────────┐
            │  web (HTTP + 정적 페이지)   slack   │
            └───────────────┬────────────────────┘
                            │ ask(question)
┌───────────────────────────▼───────────────────────────┐
│ core                                                   │
│  retrieve ──► answer ──► confidence ──► log(unanswered)│
│     ▲                                                  │
│  index (조각 + 임베딩)                                  │
└─────▲─────────────────────────────────────────────────┘
      │ sync
 data/synthetic/docs/*.md
```

- `core`는 Slack·HTTP를 모름. 입력은 질문 문자열, 출력은 구조화된 답변 객체
- 어댑터는 `core`의 출력을 채널 형식(HTML, Slack Block Kit)으로 변환만 함
- 이 분리로 웹 데모와 Slack 봇이 같은 답을 냄

### 답변 객체

```ts
type Answer = {
  status: "answered" | "pending_policy" | "unanswerable";
  text: string;
  confidence: "high" | "medium" | "low";
  citations: { docId: string; title: string; excerpt: string }[];
};
```

- `pending_policy`: 근거 문서가 "준비 중" 상태 → "정책 확정 전"이라고 안내하고 추측 금지
- `unanswerable`: 근거 부족 → 모른다고 답하고 미답변 리포트에 기록

## 6. 설계 결정

### 검색

- 조각 기준: 마크다운 제목(`##`) 단위, 너무 길면 문단 단위로 추가 분할
- 조각에 문서 제목·섹션 제목을 붙여 임베딩 → 짧은 조각의 문맥 손실 완화
- 인덱스는 JSON 파일. 문서 수십 개 규모에서 벡터 DB는 과잉
- 유사도 상위 k개(5) 선택. 하한(0.15)은 명백히 무관한 조각만 거름 → 거절 판단은 유사도가 아니라 모델 근거 판단이 담당

### 확신도

- 두 신호를 조합
  - 검색 신호: 최고 유사도, 상위 조각 간 점수 차
  - 모델 신호: 답변 생성 시 구조화 출력으로 "근거 충분 여부" 자기 판단
- 두 신호 중 약한 쪽을 따름. 모델 자기 판단만 믿지 않음
- 임계값은 평가셋으로 조정하고 근거를 `architecture.md`에 기록

### 거절

- 근거 조각에 없는 내용은 답하지 않도록 프롬프트와 출력 스키마로 이중 제한
- "모르겠습니다"도 정상 응답으로 취급 → 틀린 답보다 거절이 낫다는 원칙

### 미답변 리포트

- 확신도 낮음·거절 질문을 JSONL로 기록 (질문, 시각, 최고 유사도, 가장 가까운 문서)
- 운영 화면에서 가장 가까운 문서 기준으로 묶어 표시 → "어느 문서를 보강할지" 바로 보임

### 고객 답장 초안

- 흐름: 상담원용 답변(내부 확인) → 버튼을 누르면 전용 내장 프롬프트로 고객에게 보낼 답장 초안 생성
- 두 단계로 나눈 이유
  - 상담원 답변은 정확성·근거 확인용, 고객 답장은 표현·말투용. 한 번에 시키면 둘 다 흐려짐
  - 상담원이 근거를 확인한 뒤에만 고객 문장이 만들어짐
- 입력은 확인된 답변 + 인용 근거만. 원 문서 전체나 검색 결과는 넘기지 않음
- 프롬프트 규칙
  - 확인된 답변·근거에 있는 사실만 사용. 수치·일정·절차 추가 금지, 근거 없는 시점 약속 금지
  - 상태별 작성: 확정은 결론 먼저, 준비 중은 "확정되면 공지로 안내"만, 근거 없음은 보류 답장
  - 문서 이름·조각 번호·"상담원" 같은 내부 표현을 고객 관점 문장으로 바꿈
  - 상담원 메모 말투("~래요")를 고객에게 직접 하는 말로 바꿈
  - 첫 줄은 고정 인사말 "안녕하세요. 시네웨이브입니다." → 코드가 한 번 더 맞춤 (모델이 쓴 다른 인사는 걷어 냄)
  - 마크다운 금지, 5문장 안팎
- 코드 가드: 답장에 나온 숫자 중 확인된 답변·근거에 없는 것을 찾아 경고 (번호 목록 머리는 제외)
- 버튼을 누를 때만 생성 → 모든 질문에 호출이 두 배가 되는 것 방지
- 웹 API는 `answerId`로만 답장 요청을 받음. 클라이언트가 보낸 임의 텍스트를 모델에 넣지 않기 위함
- 초안은 편집 가능한 입력창으로 보여주고, 보내기 전 확인 문구 표시

### 모델

- 생성·임베딩 모두 OpenAI API (`openai` 공식 SDK)
- 임베딩: `text-embedding-3-small` 계열 — 문서 수십 개 규모에서 비용 대비 충분
- 생성: 구조화 출력(JSON Schema)으로 `Answer` 객체를 바로 받음 → 파싱 실패 처리 최소화
- 모델 ID는 설정 파일로 분리. 생성 모델은 구현 시점의 비용 대비 성능 좋은 소형 모델로 결정

### 공개 데모 비용 방어

- IP당 분당 요청 수 제한 (20회): 연타 방지용
  - 처음엔 6회 → 질문 하나에 답변·답장 2번이라 예시 질문 몇 개만 눌러도 걸림. 배포 후 직접 써 보고 조정
- 하루 모델 호출 상한: IP별 30회, 전체 300회. 넘으면 화면이 목업 모드로 전환하고 이유를 표시
  - IP별 상한을 먼저 확인 → 한 방문자가 전체 한도를 다 쓰지 못하고, 막힌 요청은 전체 한도를 깎지 않음
  - 캐시 적중은 모델을 부르지 않으므로 상한에 포함하지 않음
- 질문 길이 상한 (300자)
- 같은 질문 24시간 캐시: 띄어쓰기·끝 문장부호 차이는 같은 질문으로 봄
- 고객 답장 초안은 버튼을 누를 때만 생성, 한 번 만든 초안은 저장해 재사용
- API 키는 서버에만 보관. OpenAI 대시보드 사용 한도를 함께 설정

### 배포와 저장소

- Vercel(화면·API) + Supabase(Postgres + pgvector)
- 서버리스는 파일이 남지 않으므로 인덱스·미답변·답변 캐시·호출 제한을 모두 DB로
- 저장소 선택: `SUPABASE_URL`·`SUPABASE_SECRET_KEY`가 있으면 Supabase, 없으면 로컬 파일·메모리
  - core는 `Search`, `IndexRepo`, `UnansweredLog` 인터페이스에만 의존 → 테스트·CLI·배포가 같은 로직
- 검색: Supabase `match_chunks` 함수. 로컬 메모리 검색과 같은 코사인 계산 → 평가 결과가 배포에도 그대로 유효
  - 조각 수십 개 규모라 벡터 인덱스 없이 전수 비교
- 동기화: `npm run sync`가 해시 비교로 바뀐 문서만 Supabase에 반영
- 보안: 모든 테이블 RLS를 켜고 정책을 두지 않음, 함수 실행 권한은 서버 역할만 → 공개 키로는 접근 불가
- 답장 요청은 `answerId`로만 받음. 서버에 저장된 답변만 모델에 들어감
- 일시정지 방지: Supabase 무료 프로젝트는 약 7일간 요청이 없으면 일시정지
  - Vercel Cron이 하루 한 번 `/api/keepalive` 호출 → 가벼운 조회로 DB를 깨워 두고 지난 호출 제한 기록 정리
  - `CRON_SECRET` 헤더가 맞을 때만 실행
  - 그래도 DB에 닿지 못하면 화면이 목업 모드로 전환 → 데모 링크가 깨지지 않음
- 빌드: esbuild로 API를 번들해 Vercel Build Output API 형식(`.vercel/output`)으로 직접 생성
  - 소스의 `.ts` 확장자 import를 Vercel 자동 빌드에 맡기지 않기 위함

## 7. 평가

- `data/synthetic/eval/questions.jsonl`: 질문, 기대 문서, 기대 상태(answered/pending_policy/unanswerable)
- 구성: 답할 수 있는 질문, 준비 중 정책 질문, 문서에 없는 질문, 표현만 바꾼 질문
- `npm run eval` 지표
  - 검색 적중률: 기대 문서가 상위 k에 포함된 비율
  - 상태 정확도: 기대 상태와 일치한 비율
  - 잘못된 답변률: 답하면 안 되는 질문에 답한 비율 (가장 중요)
- 결과표를 `architecture.md`에 붙여 임계값 결정 근거로 사용

## 8. 화면 구성 (웹 데모)

### 상담원 화면

- 질문 입력창과 예시 질문 버튼 (처음 방문자용)
- 답변 카드: 본문, 확신도 배지, 상태 표시(준비 중·답변 불가)
- 근거 조각 펼쳐보기: 문서 제목, 인용 문장
- 고객 답장 만들기(근거 없음이면 보류 답장 만들기) → 편집 가능한 초안, 근거 밖 숫자 경고, 복사

### 정책 문서 화면

- 상담과 운영 탭 사이. 문서 목록(한글 제목 순, 준비 중 표시) + 원문
- 원문은 동기화 때 DB에 함께 저장한 것 → 상담원이 보는 문서 = 코파일럿이 근거로 검색하는 문서
- 근거 카드의 "원문 보기"로 해당 섹션까지 바로 이동 (`#/docs/<id>?s=<섹션>`)
- 문서 안의 다른 문서 참조(`refund` 등)는 해당 문서 링크로 표시
- 준비 중 문서는 상단에 "요금·일정을 약속하지 말 것" 안내

### 운영 화면

- 미답변 질문 목록 (문서별로 묶음, 건수 순)
- 문서 동기화 상태: 문서 목록, 상태(확정/준비 중), 마지막 동기화 시각
- 데모에서는 읽기 전용

### 디자인 원칙

- 업무 도구 톤: 무채색 바탕, 색은 답변 상태에만 사용 (확정 초록 · 준비 중 주황 · 근거 없음 빨강)
- 상태는 색만으로 구분하지 않음: 아이콘 + 라벨 + 상담원이 할 행동 한 줄
- 확신도는 확정 답변에만 표시. 낮으면 "인용 원문을 직접 확인" 경고
- 근거 문서는 기본으로 펼침. 근거를 보여주는 것이 신뢰의 핵심
- 검색 추적 패널: 검색된 조각과 유사도, 실제 근거로 쓴 조각을 구분해 표시 (포트폴리오 방문자가 동작 원리를 볼 수 있게)
- 예시 질문 칩은 세 상태가 모두 나오도록 구성, 칩 점 색으로 결과 상태 예고
- 라이트 모드 고정 (업무 화면 기준), 모바일(단일 열), 키보드 포커스, 동작 줄이기 설정 대응
- 한글 입력 조합 중 Enter는 전송하지 않음
- 마크다운(표·목록·굵게·제목)은 자체 렌더러로 표시: 원문을 먼저 이스케이프한 뒤 변환해서 HTML 주입 없음

### 구현 방식

- 정적 HTML·바닐라 JS (`src/web/public/`) + 표준 Request/Response 핸들러 하나 (`src/server/api.ts`)
  - 같은 핸들러를 로컬 개발 서버(`npm run dev`)와 Vercel 함수가 공유
- 프레임워크를 추가하지 않아 의존성을 최소로 유지
- API: `POST /api/ask` → `{ answer, answerId }`, `POST /api/reply` (`answerId`) → 답장 초안, `GET /api/docs` → 정책 문서 원문, `GET /api/ops` → 문서·미답변 묶음·평가 지표
- 목업 모드: API가 없으면(파일로 열기, 정적 호스팅) `mock-data.js`로 동작
  - `npm run mock`: 평가 결과(실제 모델 응답)로 목업 데이터 생성. API 키가 있으면 고객 답장 초안도 실제 모델로 만들어 캐시
  - 자유 입력은 가장 비슷한 평가 문항의 응답을 보여주고 그 사실을 화면에 표시
  - API 키 없이 볼 수 있는 데모 → 비용 방어의 1차 수단
- `?q=질문` 링크로 바로 질문, `&reply=1`이면 답장 초안까지 (데모 링크 공유용)

## 11. README 스토리텔링 구성

1. **장면**: 신입 상담원이 고객 대기 중에 환불 규정을 찾느라 문서 세 개를 뒤지는 순간
2. **문제**: 인력은 계속 바뀌고, 어떤 정보가 최신인지는 사람의 기억에만 있음 → 답이 사람마다 달라지고 고객 만족도 하락
3. **왜 AI인가, 왜 AI만으로는 안 되는가**: 검색만으로는 흩어진 규정을 묶지 못함, 생성만으로는 지어낸 답이 나옴 → 근거 기반 답변 + 거절
4. **설계**: 아키텍처 그림 한 장, 확신도·준비 중 상태·미답변 리포트를 하나씩
5. **결과**: 데모 링크·GIF, 평가 지표
6. **배운 것**: `docs/lessons.md` 요약 세 줄
